# Verify: review likes and comments · spec 0014

_Steps derived from spec 0014 acceptance criteria. Every step is written so it can fail; a step that can only pass is not a step. Run by `/check verify` on 2026-11-12 against the dev stack (customer on 3000, gateway on 3580, auth on 4580, Postgres in the `astrum-db` container). First run of 2026-11-12: **FAIL**, on one runtime defect the like press hit. Second run after the fix, the same day: **PASS**, every step below exercised and passing._

## Premise corrections

- **The like press could not succeed from the storefront (found by the first run, fixed before the second).** The client sent `PUT /api/reviews/:id/like` with the body `null` (axios stringifies the `{ arg: null }` payload of `useReviewLikes.toggle`), and `express.json()` in `apps/api-astrum/src/app.ts` rejects the JSON literal `null` with `400` and an HTML error page before any route or guard runs. Proven three ways: the storefront press answered `PUT /api/reviews/<R1>/like -> 400` with `SyntaxError: Unexpected token 'n', "null" is not valid JSON`; `curl -X PUT … -d 'null'` answers the same `400` with the same body; `curl -X PUT` with no body, or with `{}`, answers `200`. The like service itself is correct: every `curl` call in the Commands section passes. So the first run reported the like steps as FAIL or BLOCKED, and the comment steps were unaffected, because a comment `POST` carries an object and the comment `DELETE` carries no body at all. The fix landed in `useFetcher.putItem` (`arg ?? undefined`), so a route that takes no body now gets no body; the second run pressed like and unlike on the screen and the like steps below passed.
- **`{"body":"  five  "}` cannot answer `201`.** `five` is four characters after the trim, and `CreateReviewCommentDto` enforces 5 to 2000 on the trimmed body, so that body answers `400` naming `body`. The trim-then-store intent was proven with `{"body":"  seven  "}` → `201` and the stored column reading `seven`; the four character case is proven separately as a `400`.
- **Nine comments inside the hour do not make the tenth answer `429`.** `reviews.service.ts` refuses when the caller's rows in the window already number `REVIEW_COMMENT_RATE_LIMIT` (`10`), so with nine present the tenth is accepted and the eleventh answers `429`. Proven: nine rows → `201` with the counter moved, the next call → `429 REVIEW_COMMENT_RATE_LIMITED`, and the count query still answered `10`.
- **Enter from the harness needs a `char` event.** `Input.dispatchKeyEvent` with only `keyDown`/`keyUp` never activated a focused button; adding the `char` event (`text: "\r"`), or pressing Space, did. The keyboard step ran with that switch plus `Emulation.setFocusEmulationEnabled`.
- **A `click_at_xy` on the dialog's keep control looked like it left the dialog open**, because the release landed on the row control underneath once the dialog had closed. A programmatic click and a `mousePressed`/`mouseReleased` pair both closed it with no request, so that observation was a harness artifact, not a defect.
- **`comments.refused.unconfirmed` is the no-answer branch**, not the email confirmation branch: `classifyCommentRefusal` returns `unconfirmed` when the gateway gave no answer at all, while `emailNotConfirmed` raises no toast of its own because the shared `useFetcher` interceptor already did. Both behaviours match AC-5 and AC-9.

## Run notes

Run of 2026-11-12 on the dev stack that was already up (`customer` 3000, `api` 3580, `auth` 4580, `worker` 5580, `astrum-db` on 5432), with migration `20261112164114_review_likes_and_comments` applied at 16:41 and both new tables, their indexes and their cascades read back from the container.

Sessions: no password was typed. A `session:<sid>` record was written to `astrum-redis` and the `__auth` JWT signed with `JWT_SECRET` from `apps/api-astrum/.env` (the root `.env` carries a different secret and its token is refused), then set on `localhost` through CDP `Network.setCookie`; the same three cookies drove every `curl` call. `GET /api/users/me` answered for all three accounts, which is how the sessions were confirmed before any step ran.

Seeded data: R25 = `review-check-2` was given 60 comments by SQL from three customers, 35 of them deleted afterwards so the same review served the clamp read and the 25 comment paging case; `seed-r60-10` and `seed-r60-11` share one `createdAt` for the id tiebreak; `seed-r1-b` is B's comment on R1; `review-check-3` was flipped to `REJECTED` with one `UPDATE`; the rate limit used seven SQL rows on top of two comments the run created through `POST`, and those seven were deleted afterwards, with both counters resynced from their child rows by the closing SQL of the fixture block.

Degraded paths: the failed liked set was produced with `Network.setBlockedURLs ['*review-likes*']` and the failed thread read with `['*comments*']`, both failing at the transport the way `Fetch.failRequest` does, and both cleared afterwards; the busy and optimistic states needed `Network.emulateNetworkConditions` at 900 and 1200 ms latency, which was reset to no throttling after each batch.

Harness switches: `Emulation.setFocusEmulationEnabled` for the Tab walk, and `Input.dispatchKeyEvent` with a `char` event (or Space) to let a synthetic press activate a focused button.

Not observed: the like success path on any card, the third press on an in-flight like, and the like refusal branch for a `PENDING` account, all for the one `400` this run found; the rate limited refusal toast in Russian (its branch is proven at the API level and its copy is present in both catalogs).

Defect found outside this feature's scope: none. The `400` belongs to this feature, because its own hook builds the request, so it is reported against the like steps rather than as a deferred item.
