# 0019. Handover by the courier

**Date**: 2026-11-14
**Status**: In Progress

_This is the build spec. The decision record (context, options, rationale) lives in [rationale.md](rationale.md); the verification steps live in [verify.md](verify.md)._

## Summary

A courier order carries an address instead of a point, so the counter's queue cannot serve it and only a seller could close one. This decision gives a courier a pool of courier parcels that are on their way and taken by nobody, one press to take one, and the delivery address that comes with it only after taking it. A claimed parcel is handed over or cancelled with the same stock and money rules the counter already uses, and it can be given back to the pool. One nullable column records who took a parcel, and the order keeps that id after the handover, so the courier who delivered it is on the order itself.

## Requirements

**User stories**:

- As a courier, I want to see the courier parcels that nobody has taken so that I can pick one up without a dispatcher.
- As a courier, I want the delivery address only on the parcels I have taken so that no other courier reads where I am going.
- As a courier, I want one press to record the handover, and one to record a refusal at the door, so that the parcel is closed while I stand there.
- As a courier, I want to give a parcel back to the pool so that a parcel I cannot deliver does not die on my account.
- As the shop, I want the money a courier collects at the door recorded on the order, so that a delivered parcel stops reading as unpaid.

**Acceptance criteria** (the contract):

- **AC-1**: `Order` gains `courierUserId String?`, a plain scalar with no relation, which is the shape `Order.userId` already has, plus `@@index([courierUserId])`. The same edit goes into all four schema files (`packages/Astrum-db/prisma/schema.prisma` and the three copies under `apps/api-astrum`, `apps/auth-astrum` and `apps/worker`), which are byte identical today at 486 lines with md5 `4aa7227…`, and they stay byte identical after it. One migration, `20261114130000_courier_claim`, adds the nullable column and its index; no backfill runs, because every order in the database reads null. `pnpm prisma:generate` rebuilds all four clients through turbo, because the root `pnpm db:generate` filters `@astrum/db` and writes only `packages/Astrum-db/generated`, leaving the three app clients behind; `pnpm check-types` fails while any of them is stale. The migration folder is `packages/Astrum-db/prisma/migrations/20261114130000_courier_claim/` and its `migration.sql` runs `ALTER TABLE "Order" ADD COLUMN "courierUserId" TEXT;` plus `CREATE INDEX "Order_courierUserId_idx" ON "Order"("courierUserId");`.
- **AC-2**: `GET /api/staff/courier/orders` mounts `requireCourier` only, because a read stays open to a `PENDING` account, as spec 0017, AC-9 set for the other staff reads. It answers `200 { orders, page, limit, total, totalPages }`. `scope` takes `mine` or `available` and defaults to `mine`; the value is checked in the controller before the service call, because `validateDto` reads `req.body` only (`apps/api-astrum/src/middlewares/validateDto.ts:24`), and any other value, a repeated `scope` that arrives as an array included, answers `422 VALIDATION`. Both scopes read only rows whose `status` is `SHIPPED` and whose `shippingMethod.isPickup` is false; `mine` adds `courierUserId` equal to the caller's id, `available` adds `courierUserId: null`. Rows are ordered by `createdAt` ascending with `id` ascending as the tiebreak, `page` defaults to 1, `limit` to 20 and is clamped to 50 by the existing `parsePagination` from `apps/api-astrum/src/common/helpers/pagination.ts`, and `total` is a `count` over the same filter the page reads. An empty answer is `{ orders: [], page, limit, total: 0, totalPages: 0 }`. The five routes are added to the existing `staffRoutes` router in `apps/api-astrum/src/modules/staff/staff.routes.ts`, which is already mounted once inside the `app.use("/api", authenticateToken, ...)` chain of `src/app.ts`, so no second mount and no second `authenticateToken` run is introduced.
- **AC-3**: Every answer of these five routes carries the order row in exactly this shape: `{ id, createdAt, status, paymentStatus, paymentMethod, handedOverAt, grandTotal, currency, courierUserId, deliveryDate, deliveryAddress, orderItems: [{ id, name, previewImage, quantity, price, currency, status }] }`, built by one mapper so the list and the writes cannot drift apart. `grandTotal` and every `price` reach the browser through `toMoney` from `apps/api-astrum/src/common/helpers/money.ts`, so they are numbers with at most two decimals and never decimal strings; `createdAt`, `deliveryDate` and `handedOverAt` reach JSON as ISO strings or `null`. `deliveryAddress` is the stored address **only on a row whose `courierUserId` equals the caller's id**, and `null` on every `available` row and on every row the caller has released, because the claim is what buys the address. The row carries no `userId`, no buyer name, email or phone (an order has none), no `pickupPointId`, no shipping method id or name, no business id or name and no `idempotencyKey`.
- **AC-4**: `POST /api/staff/courier/orders/:orderId/claim` mounts `requireActiveAccount`, then `requireCourier`, then the controller, in that order, and takes no body. It runs one transaction with `ORDER_TRANSACTION_OPTIONS`, calls `lockOrder`, and reads the order by id alone with the select of AC-3 plus `courierUserId` and `shippingMethod.isPickup`, through one `classifyCourierOrder` function that the other three writes share. The classification answers in this order: a missing order and an order whose method is a pickup answer the same `404 ORDER_NOT_FOUND`, so a courier never learns a counter parcel exists; a row already claimed by the caller, still `SHIPPED` and not handed over answers `200 { order }` and writes nothing, so a second press is idempotent; a row whose `handedOverAt` is set answers `409 ALREADY_HANDED_OVER`; a row claimed by another courier answers `409 ALREADY_CLAIMED`; a row in any other status answers `409 ORDER_NOT_SHIPPED`. A claim writes `courierUserId = userId` and answers `200 { order }` in the shape of AC-3 with the address filled, built from the row already held under the lock, so no second read can disagree with the write, and writes one log line `staff.courier.claimed` carrying `userId`, `orderId` and `resultCode: "OK"`. Those branches cover every state a row can be read in, and a state none of them matches is a server fault (`handleErrors` answers `500`), never a scenario. The order lock decides the race: two couriers pressing at once are serialised, the first reads `courierUserId` null and writes, the second reads the winner's id and answers `409 ALREADY_CLAIMED`.
- **AC-5**: `DELETE /api/staff/courier/orders/:orderId/claim` mounts the same chain and runs the same transaction, the same lock and the same `classifyCourierOrder` as AC-4, then writes `courierUserId = null` and answers `200 { order }` in the shape of AC-3 with `deliveryAddress: null`. Its ladder is AC-4's with one difference: a row the caller does not hold, which covers a missing order, a pickup order, another courier's parcel and a parcel the caller already released, answers `404 ORDER_NOT_FOUND` instead of `409 ALREADY_CLAIMED`, because a release of something the caller does not hold has nothing to say about who holds it; `409 ALREADY_HANDED_OVER` and `409 ORDER_NOT_SHIPPED` follow as in AC-4. A release writes `staff.courier.released`. A second press therefore writes nothing and answers `404`, and the screen reads again both sections on every refusal, so the vanished row leaves the list instead of being offered again. `courierUserId` is the single field both directions write, and the release keeps no record beyond its log line.
- **AC-6**: `PATCH /api/staff/courier/orders/:orderId/handover` mounts `requireActiveAccount`, then `requireCourier`. It works in one transaction with `ORDER_TRANSACTION_OPTIONS` and `lockOrder`, reads the parcel through the same `classifyCourierOrder` of AC-4, and refuses along one fixed chain where every refusal writes nothing: a missing order, an order whose `shippingMethod.isPickup` is true, and an order whose `courierUserId` differs from the caller's id all answer `404 ORDER_NOT_FOUND`, because a counter parcel is not a courier's business and an unclaimed or foreign parcel is not his to close; an order whose `handedOverAt` is not null answers `409 ALREADY_HANDED_OVER`; an order whose `status` is not `SHIPPED` answers `409 ORDER_NOT_SHIPPED`. A call that passes moves every line of the order whose status is `SHIPPED` to `DELIVERED` with `receiptDate` set to one server timestamp taken inside the transaction, leaves every other line untouched, calls `recomputeOrderStatus`, writes `handedOverAt` with that same timestamp when the returned status is `DELIVERED` and the column is null, and answers `200 { order }` in the shape of AC-3 with the address still in it. It writes one structured log line `staff.courier.handed_over` carrying `userId`, `orderId`, `deliveredLineCount`, `resultCode: "OK"` and, when AC-7 recorded money, `collectedAmount` and `collectedCurrency`; a refusal writes `staff.courier.handover_refused` with the same ids and the refusal code. The lock makes two presses on one parcel safe: the first commits, the second reads `handedOverAt` and answers `409 ALREADY_HANDED_OVER`. `courierUserId` stays as it is, so the order keeps the id of the courier who delivered it.
- **AC-7**: The handover records the money a courier collects at the door. When the order's `paymentMethod` is `CASH` or `CARD_ON_DELIVERY`, its `paymentStatus` is `PENDING`, and at least one line became `DELIVERED`, the same transaction writes `paymentStatus = PAID` by passing it to the existing `recomputeOrderStatus(tx, orderId, "PAID")` call, which already writes the order status from the lines in one update (`apps/api-astrum/src/modules/order/order-status.helpers.ts:63`), and the handover log line carries `collectedAmount`, the order's `grandTotal` as a string at two decimals through `toFixed(2)`, the form the refund warning already prints, and `collectedCurrency`, the order's `currency`, because the courier takes the whole bill at the door. Every other case leaves the payment untouched, so an order already `PAID` and an order whose method is neither of those two keep their `paymentStatus` and their attempts, and their handover line carries neither field. No `Payment` attempt row is written, because `PaymentProvider` holds `STRIPE` alone and a cash attempt would need a new enum value and a migration; the log line and `Order.paymentStatus` are the record, and the attempt row is owed work in Follow-up. The write cannot run twice on one order, because the second handover answers `409 ALREADY_HANDED_OVER` before reaching it, so the money is recorded once.
- **AC-8**: `PATCH /api/staff/courier/orders/:orderId/cancel` mounts the same chain, uses the same transaction and lock, and carries the same `SHIPPED` precondition as the handover. Before the transaction opens it runs the ownership read (a missing, pickup or foreign order answers `404 ORDER_NOT_FOUND`) and then the existing `expireSessionForCancel` from `modules/payment/payment.cancel.ts`, because the provider call must never run while the order row is locked. Inside the transaction its chain is `404 ORDER_NOT_FOUND` for a missing, pickup or foreign order, then the cancellable set of lines whose status is `PENDING`, `CONFIRMED` or `SHIPPED` read under the lock with a private select that carries `productId` and `userId` on top of the AC-3 shape, because `returnOrderStock` needs the product of every cancelled line and the refund warning names the buyer, and neither field reaches the answer, then `409 NOTHING_TO_CANCEL` when that set is empty, which covers the second press and an order whose every line is already delivered, then `409 ORDER_NOT_SHIPPED` for any status other than `SHIPPED`. A call that passes cancels exactly those lines, returns their stock through the existing `returnOrderStock`, calls `recomputeOrderStatus`, leaves every line in `DELIVERED`, `CANCELLED`, `OUT_OF_STOCK`, `RETURNED`, `BACKORDERED` or `REPLACED` alone, resolves the payment as the counter cancel does (attempts in `PENDING` or `FAILED` become `CANCELLED`, and the order's `paymentStatus` becomes `CANCELLED` when it read `PENDING` or `FAILED`), and answers `200 { order }`. When the order read `PAID` it stays `PAID` and one `payment.refund_owed` warning is written with `reason: "courier_cancel"`, `orderId`, `buyerUserId` from `Order.userId`, `actorUserId` (the courier), `amount` summed over exactly the cancelled lines with the delivery price excluded, `currency` and `cancelledLineCount`. No `pointId` is written, because a courier has none. Success writes `staff.courier.cancelled`; a refusal writes `staff.courier.cancel_refused` with the refusal code.
- **AC-9**: The code the counter and the courier share moves into `apps/api-astrum/src/modules/staff/staff-order.helpers.ts` in the same change, and both services import it: the cancellable status list, the sum of cancelled lines at two decimals, the block that cancels a set of lines and returns their stock, the block that delivers the `SHIPPED` lines of one order with one timestamp, and the block that resolves the payment of a cancel (attempts, order status and the refund warning, taking `reason`, `actorUserId`, the buyer id, the amount, the currency, the cancelled line count and an optional `pointId` that the counter fills and the courier omits). `point-order.service.ts` keeps its own point checks, its own request scoping, its own `PICKUP_POINT_INACTIVE` branch and its own log event names, and every answer it gives today stays byte for byte what it is, including the `pointId` on its refund line and the `userId` and `productId` its cancel reads; its three suites (`point-order.service.spec.ts`, `staff.routes.spec.ts` and `point-handover.integration.spec.ts`) pass without an edit, which is the proof the extraction did not touch the counter. `courier-order.service.ts` is a new file carrying the courier chain and no copy of the shared blocks.
- **AC-10**: `apps/customer/src/hooks/staff/courierOrder.types.ts` declares `CourierOrder` in the shape of AC-3 with `deliveryAddress: string | null`, plus `CourierOrdersPage`. `useCourierOrders(scope)` reads `/staff/courier/orders?scope=<scope>&page=<n>&limit=20` through `getData`, appends the next page on `showMore`, and drops every accumulated page and reads again page one on `mutate`, exactly as `usePointOrders` does. `useCourierOrderAction` sends `claim` with `postItem(path, { arg: {} })`, `release` with `deleteItem(path)`, which takes a bare url, and `handover` and `cancel` with `patchItem(path, { arg: {} })`, holds one pending action, and returns before a second send. Both catalogs gain `staff.courier.queue` with the same keys in `en.json` and `ru.json`, and `staff.courier.queueLine` is deleted from both because nothing reads it after AC-11. Labels that already exist are reused, never copied: `orders.number`, `orders.deliveryDate`, `orders.deliveryAddress` and `orders.itemStatus` through `itemStatusKey` (`orders.handedOverAt` is not one of them, because both scopes read `SHIPPED` orders and a handed over order is `DELIVERED`, so no card can print it). The new namespace carries, with the same keys in both files: `mineTitle`, `availableTitle`, `refresh`, `loading`, `emptyMine`, `emptyAvailable`, `failureTitle`, `failureText`, `retry`, `showMore`, `totalLabel`, the four control labels, the four busy labels, the four dialog titles, texts and confirm labels, `keep`, four success texts, `cancelPaidText`, and `refusals` with `orderNotFound`, `notShipped`, `alreadyHandedOver`, `alreadyClaimed`, `nothingToCancel`, `notCourier`, `roleUnavailable`, `accountStatusUnavailable`, `validation`, `generic` and `retry`.
- **AC-11**: `/courier` keeps the states spec 0017 gave it (skeleton, no role screen, failure screen with Retry); `CourierCard`, which holds the placeholder line at `features/pages/CourierWorkspace/components/CourierCard.tsx:16`, keeps its heading and the content container and renders the queue block where that line stood, and the block renders two sections: `staff.courier.queue.mineTitle` listing the caller's claimed parcels and `staff.courier.queue.availableTitle` listing the pool, each with its own `useCourierOrders` instance, its own refresh control, its own empty text, its own `Show more` hidden while `page >= totalPages`, and its own failure screen with Retry, so one section's failure never hides the other's rows. ## Decision

**Chosen option**: Option 2: the courier claims a parcel before he may see it or close it.

A courier gets five routes on the existing staff router (`GET /api/staff/courier/orders`, `POST` and `DELETE /api/staff/courier/orders/:orderId/claim`, and `PATCH /api/staff/courier/orders/:orderId/handover` and `cancel`), one new nullable column `Order.courierUserId` with an index, one migration, and a service that reuses the counter's shared write blocks without copying them. The delivery address reaches a courier only on a parcel he has claimed, and `courierUserId` stays on the order after the handover, so the order records who delivered it.

**Implementation skills**: none installed that shape this decision. The repository conventions in `AGENTS.md` (module per folder, `authenticateToken` at the mount, the error body shape, the order transaction rules) and the storefront coding standard in `apps/customer/AGENTS.md` (`S1` to `S5`) govern the build and are followed through those files rather than as a separate skill.

## Feature design

**Data model sketch**:

| Entity | Field | Use here | Change |
| --- | --- | --- | --- |
| `Order` | `courierUserId` | who took the parcel; `null` means it sits in the pool | **new**, nullable, plain scalar, indexed |
| `Order` | `status` | `SHIPPED` is the only status either scope reads and either write accepts | none |
| `Order` | `shippingMethodId` → `shippingMethod.isPickup` | `false` is what makes an order a courier order, and the ownership proof every route checks | none |
| `Order` | `deliveryAddress` | the address of a claimed parcel, `null` in every pool answer | none |
| `Order` | `deliveryDate` | the date printed on the card | none |
| `Order` | `paymentMethod`, `paymentStatus` | money due at the door, recorded at the handover | none |
| `Order` | `handedOverAt`, `grandTotal`, `currency` | as at the counter | none |
| `OrderItem` | `status`, `receiptDate` | `SHIPPED` to `DELIVERED` with one timestamp, or the cancelled set | none |
| `Courier` | `userId` | the role `requireCourier` reads on every call | none |

`courierUserId` is a plain scalar, not a foreign key, because `Order.userId` is one too and the two read the same way. The consequence is named in Consequences: a deleted account leaves its id on the order, exactly as `User` deletion already leaves `Order.userId` behind.

**State transitions**:

The claim is a field on the order, not a status, so the order status machine of spec 0016 is untouched:

| From | To | Trigger | Writer |
| --- | --- | --- | --- |
| `courierUserId` null | the caller's id | a courier presses take on a `SHIPPED` courier parcel | claim (this spec) |
| the caller's id | null | the courier gives the parcel back | release (this spec) |
| `SHIPPED` line | `DELIVERED` | the claiming courier hands the parcel over | courier handover (this spec) |
| `PENDING`, `CONFIRMED`, `SHIPPED` line | `CANCELLED` | the claiming courier records a refusal at the door | courier cancel (this spec) |

The order status stays a pure mirror of its lines through `recomputeOrderStatus`, so a handover closes the order as `DELIVERED` and a cancel closes it as `CANCELED` when nothing active remains. No route writes `Order.status` by hand. A buyer cancel or a payment expiry on a claimed order leaves `courierUserId` set and moves the status away from `SHIPPED`, so the parcel drops out of both scopes and every write refuses it on its status check; the stale id on a closed order is a note, not a leak.

**Key invariants**:

- Both scopes hold courier parcels only: `shippingMethod.isPickup` false, status `SHIPPED`. A pickup order never appears in either list and never answers to a courier write; it answers `404 ORDER_NOT_FOUND`.
- The claim is the ownership proof. `courierUserId` equal to the caller is required by handover, cancel and release, and `null` is required by claim; no id from the request body or query is ever accepted.
- The address leaves the server only on a row the caller claimed. Every pool row and every released row carries `deliveryAddress: null`, and the same mapper produces both.
- All four writes run in one transaction under `lockOrder` and read the parcel through the same `classifyCourierOrder`, so two couriers pressing at once cannot both win, and the row a write answers with is the row it wrote.
- One server timestamp per handover feeds both `receiptDate` and `handedOverAt`, and `handedOverAt` is written once, by the first transaction that leaves the order `DELIVERED`.
- A delivered line is never cancelled and never returns stock, and the cancellable set is read under the lock, never taken from the request.
- Money is recorded once, only for a method that collects at the door, only while the order reads `PENDING`, and only on a handover that moved a line.
- A cancel of a paid order keeps `paymentStatus = PAID` and leaves one `payment.refund_owed` warning naming the actor, the buyer and the amount. No route refunds anything.
- Neither write can collide with the shipping pass, which moves `CONFIRMED` lines and takes no order lock, because both courier writes act on `SHIPPED` orders only. The sets are disjoint by construction.
- No buyer identity reaches any answer, the screen or an error message.
- The courier surface answers no point, no point state and no `PICKUP_POINT_INACTIVE`: a courier is an account, not a facility, and a shipping method switched off after the order changes nothing for a parcel already on its way.

**Security model**:

Every route sits behind the `__auth` session cookie. `requireCourier` reads the caller's own `Courier` row by `userId` on every request and puts the role on the request, refusing an account without it with `403 NOT_COURIER` and answering `503 STAFF_ROLE_UNAVAILABLE` when the read fails, so an outage never reads as a missing role. The four writes carry `requireActiveAccount` first, so a `PENDING` account is refused `403 EMAIL_NOT_CONFIRMED` before its role is read.

The claim is what bounds what a self granted role can see. Spec 0017 made the grant self service, so any confirmed account can become a courier, and spec 0018 recorded that such an account could hand over or cancel a point's parcels. Without a claim this feature would have handed every courier the delivery address of every parcel in flight, which is a registry of where buyers live; with it, a courier reads the addresses of the parcels he took and nothing else, and the pool answer carries no address at all. The remaining exposure is the pool itself, a list of order numbers, items and dates that a fake courier walks one claim at a time: hold a claim and he reads one address, release it and take the next and he reads another. The claim therefore bounds accidental and casual reading and it attributes every parcel to an account; it is not a defence against an account made for the purpose, and the rule for who may grant a staff role, owed since spec 0017, is that defence.

No payment, health or regulated data enters the feature: the delivery address is personal data of the ordinary kind, stored as free text since spec 0013, and no compliance scope applies. No new rate limit is added: every call needs a live session and a role row, a repeat writes nothing, and the `SHIPPED` precondition bounds what either write can touch.

**Configuration required**:

None. No new environment variable, secret or dependency is introduced.

## Consequences

**Positive**:

- The delivery address reaches only the courier who took the parcel, which is what makes a self granted role survivable while the rule for who may grant it stays owed.
- A delivered cash order stops reading as unpaid: the money a courier takes at the door is on the order the same moment the parcel closes.
- The order keeps `courierUserId` after the handover, so who delivered a parcel is on the record; spec 0018 could only log that for the counter, and its audit table follow up stays open there.
- The write blocks are shared with the counter, so the two handover surfaces cannot drift on stock, locks or the refund warning.
- The claim needs no new table: one nullable column carries the assignment in both directions.

**Negative / tradeoffs**:

- The scope row said every courier reads one shared list. This decision contradicts that sentence, which is why the row is rewritten in the same pass; the pool now shows a courier the parcels he has not taken, without addresses.
- A claimed parcel that nobody delivers stays claimed until its courier releases it or an operator clears the column. There is no expiry and no dispatcher, and a courier who stops working leaves his claims behind.
- The money at the door is recorded as `paymentStatus = PAID` with no `Payment` attempt row, because a cash attempt would need a new `PaymentProvider` value and a migration. The ledger therefore has two shapes of paid, and the log line is the only trail for the cash one.
- The counter's handover still leaves a cash order unpaid. This spec changes the courier path only, and the asymmetry is owed work in Follow up.
- One migration and four schema copies plus four regenerated clients is the first schema change since spec 0017, and it touches the auth and worker copies that this feature never reads.
- The pool read filters `status` and `courierUserId` on an index that covers only `courierUserId`, so the status is checked over every unclaimed order. It is right at this size and needs a composite index once the pool grows.
- A release keeps no record beyond a log line, so a parcel that changes hands between couriers leaves no trace of the first one.
- Each section keeps its own accumulated pages, so a refresh starts from page one, and any successful action returns both sections to page one on purpose, because resuming from a shifted offset would silently skip a parcel.
- The claim bounds what a courier meets by accident, not what a determined account can reach: claim, read the address, release, take the next and the whole pool is readable one address per press. Persisting every release and refusing a re-claim of the same order would close only the least interesting step of that walk, so the rule for who may grant a role stays the real fix.
- The delivery date prints in UTC, which is correct only because the checkout writes noon in the buyer's zone (spec 0009's habit): the calendar date survives for a buyer between UTC-11 and UTC+12, and a buyer further east would see the parcel dated a day earlier.

**Neutral**:

- The tag is GA, so `/check verify`, `/test` and a review on another model follow the build.
- The counter's screen, its components and its tests are read by the extraction in build task 2 and must stay green; that is the regression proof, not a rewrite of spec 0018.
- The courier's `GET /api/staff/courier` role read, the onboarding page and the navigation items of spec 0017 are unchanged.
- The placeholder line `staff.courier.queueLine` and its catalog key go away, which closes the last "this arrives later" copy on the staff pages.
- No new environment variable, secret or dependency is introduced.
