# Astrum

[English](README.md) · [Русский](README.ru.md)

Платформа электронной коммерции в монорепозитории: витрина на Next.js, API-шлюз на Express, отдельный сервис аутентификации на NestJS и общая схема данных Prisma и PostgreSQL. Весь проект запускается одной командой `docker compose`; каждый компонент, кроме базы данных, работает в нескольких репликах за балансировщиком.

> **Стадия: работа над MVP.** Уже работают каталог, корзина, личный кабинет, оформление заказа и подтверждение почты: сервер определяет цену, состав и наличие товаров в заказе, а повторная отправка запроса не создаёт дубликат. Впереди — завершение сквозного сценария: способы доставки через API, выполнение заказов и оплата.

## Что работает

- **Каталог**: 4,7 тысячи товаров (демоданные), 10 категорий, страницы товаров с характеристиками, рекомендациями, постраничной загрузкой по курсору и поиском внутри категории
- **Аккаунт**: регистрация и вход (argon2), сессия в HttpOnly-cookie, защищённые маршруты витрины и API
- **Подтверждение почты**: письмо со ссылкой, действительной 24 часа, проходит через брокер сообщений и worker; витрина показывает экран проверки почты и позволяет отправить письмо повторно с ограничением частоты. Пока аккаунт имеет статус `PENDING`, заказы, отзывы и изменение профиля недоступны
- **Профиль**: изменение данных, смена пароля, удаление аккаунта
- **Корзина и список желаний**: добавление товаров, изменение количества с проверкой остатка, удаление и выбор позиций для оформления заказа
- **Заказы**: сервер определяет цену, состав и наличие товаров; позиции содержат только `productId` и `quantity`, суммы хранятся как `Decimal`, остатки списываются в транзакции, а отказ возвращается с кодом (`OUT_OF_STOCK`, `CART_MISMATCH`). Повторный запрос с тем же `Idempotency-Key` возвращает первый заказ, заказанные позиции удаляются из корзины на сервере, а страницу заказа может открыть только его владелец. Отмена и переходы статусов заказа работают; выполнение заказов пока не реализовано
- **Отзывы**: API проверяет покупку (оставить отзыв можно только после `DELIVERED`), разрешён один отзыв на позицию заказа и предусмотрена модерация; экран отзывов пока использует тестовые данные

## Архитектура

Caddy выполняет две роли: публичной точки входа и внутреннего балансировщика перед API-шлюзом. Компоненты не обращаются друг к другу напрямую по одному адресу — каждый переход проходит через Caddy, поэтому балансируются и реплики API. Сессии всех реплик хранятся в Redis, а письма с подтверждением отправляются через RabbitMQ отдельному worker.

```
браузер
  │  HttpOnly-cookie __auth
  ▼
proxy (Caddy) · :80 / :443         публичная точка входа, TLS
  ▼
apps/customer ×2   Next.js 16 · :3000 (standalone)
  │  /api-gateway/*  →  proxy:3580
  ▼
proxy (Caddy) · :3580              внутри сети, порт не опубликован
  ▼
apps/api-astrum ×3   Express 5 · :3580 ─── /api/auth ───▶ apps/auth-astrum   NestJS 11 · :4580
  │            │                                                  │
  │            └──── session:<sid> ──▶ redis 7 · :6379 ◀──────────┘
  │                                                               │
  │                                        account.confirmation.requested
  │                                                               ▼
  │                                                     rabbitmq 4 · :5672
  │                                                               ▼
  │                                    apps/worker · :5580 ──▶ mailpit · :8025
  │                                                               │
  └───────────────────────────┬───────────────────────────────────┘
                              ▼
                     PostgreSQL 16 · Prisma 7
                      packages/Astrum-db
```

Реплики не хранят состояние в памяти процесса: сессия — это подписанный JWT в cookie и запись `session:<sid>` в Redis. Шлюз проверяет её при каждом защищённом запросе, поэтому выход из аккаунта сразу отзывает сессию на всех трёх репликах. Redis находится в той же сети compose, но без тома и персистентного хранилища: после перезапуска контейнера все активные сессии завершаются. Caddy находит реплики через DNS compose (`dynamic a`), проверяет каждую с помощью `GET /health` (Postgres и Redis) и исключает неисправные из балансировки; пока действует окно проверки, запрос повторяется на соседней реплике. Размер пула подключений Prisma ограничен параметром `DB_POOL_SIZE`, а отдельный одноразовый сервис применяет миграции до запуска приложений.

Подтверждение почты проходит через брокер: после регистрации и повторной отправки `apps/auth-astrum` публикует событие `account.confirmation.requested` в exchange `astrum.events`; после смены адреса то же делает шлюз. `apps/worker` получает событие из очереди `mail.confirmation`, создаёт одноразовую ссылку на 24 часа (в базе хранится только sha256 токена, сам токен остаётся в письме) и отправляет письмо через SMTP. Если `SMTP_URL` не задан, письмо записывается в `MAIL_OUTBOX_DIR`. После неудачной отправки письмо возвращается в очередь ожидания через 60, 300 и 900 секунд; после четвёртой попытки оно попадает в `mail.confirmation.dead` вместе с текстом последней ошибки. Пока аккаунт имеет статус `PENDING`, шлюз возвращает `403 EMAIL_NOT_CONFIRMED` для запросов заказов, отзывов и изменения профиля; вход, каталог и корзина остаются доступны. В production-стеке Mailpit используется как SMTP-сервер, его интерфейс доступен по адресу `http://localhost:8025`.

| Сервис    | Порт  | Доступность                         | Реплики |
|-----------|-------|-------------------------------------|---------|
| `proxy`   | 80/443 | извне                              | 1       |
| `customer`| 3000  | только внутри `astrum`              | 2       |
| `api`     | 3580  | только внутри, через `proxy`        | 3       |
| `auth`    | 4580  | только внутри, из `api`             | 1       |
| `worker`  | 5580  | только внутри                       | 1       |
| `rabbitmq`| 5672  | только внутри                       | 1       |
| `mailpit` | 8025  | извне, только в production-стеке    | 1       |
| `redis`   | 6379  | внутри сети, в dev также с хоста    | 1       |
| `db`      | 5432  | только внутри                       | 1       |

Обоснование выбора и рассмотренные альтернативы (Swarm, nginx, Traefik) описаны в [ADR-0003](docs/adr/0003-container-topology-and-load-balancing.md).

## Быстрый запуск

Понадобятся Node 24+, pnpm 12.8+ и Docker.

### Разработка

```bash
pnpm install
cp .env.example .env     # заполните JWT_SECRET и пароль базы данных
pnpm db:up               # Postgres 16 и Redis 7 в Docker
pnpm prisma:migrate:deploy
pnpm db:generate
pnpm dev                 # Postgres, Redis, RabbitMQ и Mailpit в Docker; затем витрина :3000 · API :3580 · auth :4580 · worker :5580
```

Демонстрационный каталог загружается из xlsx-файла скриптом `seed:excel`; файлы базы данных не входят в репозиторий, поэтому после клонирования магазин будет пустым.

### Весь стек в Docker

```bash
cp .env.prod.example .env.prod   # заполните пароль базы данных и JWT_SECRET
pnpm docker:prod:build           # собрать образы
pnpm docker:prod:up              # http://localhost, почта на :8025
pnpm docker:prod:logs            # логи всех сервисов
pnpm docker:prod:down            # остановить стек
```

- Домен задаётся в **корневом `.env`** (`DOMAIN=http://localhost` для локальной разработки, `DOMAIN=example.com` для сервера; Caddy самостоятельно выпустит сертификат). Переменные контейнеров хранятся отдельно в `.env.prod`, поскольку это два разных уровня подстановки переменных.
- Внутри сети сервисы доступны по именам compose (`db`, `auth`, `api`, `proxy`), а не по `localhost`.
- Увеличить число реплик: `docker compose -f docker-compose.prod.yml up -d --no-deps --scale api=5 api`.
- `pnpm dev` и `docker:prod:up` используют один том Postgres (`POSTGRES_VOLUME`), поэтому запускать их одновременно нельзя.
